# pg-s3-backup

Самодостаточный образ: **бэкап всех баз PostgreSQL → сжатие zstd → выгрузка в S3**, с проверкой
целостности и ретеншном. Отдельный репозиторий — не зависит ни от какого проекта.
Подключается к любому стеку одной ссылкой на образ + переменными окружения.

```
Dockerfile                      # postgres-клиент + rclone + zstd + скрипт
backup.sh                       # вся логика (цикл, сжатие, S3, проверки, retention)
docker-compose.example.yml      # как подключить: только image + environment
stack.env.example               # пример env-файла (KEY=VALUE), см. «Env-файл»
docker-compose.test.yml         # локальный стенд: PG 15/16/17/18 + S3, см. «Тесты»
test/                           # сиды по версиям, проверки восстановления, прогон
.github/workflows/build.yml     # CI: тесты (PG 15..18) -> сборка и пуш образа (Docker Hub + ghcr.io)
Makefile                        # локальные build/push и test-* цели
AGENTS.md                       # краткая карта репозитория для агентов/разработчиков
```

## Что делает (по шагам, всё пишется в stdout → `docker logs`)
1. Ждёт готовности БД (`pg_isready`).
2. Раз в `INTERVAL` секунд перечисляет все базы (`pg_database`).
3. Каждую: `pg_dump -Fc -Z0` → внешний `zstd` по всему архиву → `<db>.dump.zst`.
4. **Проверяет целостность** (см. ниже): `zstd -t` + `pg_restore -l`.
5. Загружает в `s3://<bucket>/<prefix>/<db>/<UTC>.dump.zst`.
6. Сверяет размер объекта в S3 (`head-object`) с локальным.
7. Оставляет `KEEP` последних копий каждой базы; лишние удаляет.
8. Дополнительно `_globals/<ts>.sql.zst` (роли/привилегии, без паролей).

## Сборка образа
Через CI (2 этапа, `.github/workflows/build.yml`): job **test** прогоняет весь стенд (PG 15/16/17/18 +
S3), и только при успехе job **build** собирает и пушит образ сразу в два реестра:

| Реестр | Образ | Авторизация при push |
|---|---|---|
| Docker Hub | `xjl00/backup-postgres-s3` | секреты `DOCKERHUB_USERNAME` + `DOCKERHUB_TOKEN` |
| ghcr.io | `ghcr.io/xjl0/backup-postgres-s3` | штатный `GITHUB_TOKEN` (секретов не нужно) |

Образы **публичные** — `docker pull` работает без авторизации. Но **push в Docker Hub требует токена
даже для публичного репозитория**: анонимный push Hub не принимает. Один раз заведите секреты
репозитория (Settings → Secrets and variables → Actions):

- `DOCKERHUB_USERNAME` — ник на Docker Hub (`xjl00`);
- `DOCKERHUB_TOKEN` — Access Token из Hub (Account settings → Personal access tokens) с правом
  **Read & Write**. Обычный пароль не подойдёт: у аккаунтов с 2FA вход по паролю отключён.

> **Про публичность.** В Docker Hub репозиторий создаётся автоматически при первом push и сразу
> публичный. А вот пакет в ghcr.io первый push через `GITHUB_TOKEN` создаёт **приватным** — для
> анонимного `docker pull` один раз переключите: репозиторий → Packages → пакет → Package settings →
> Change visibility → Public (либо привязать пакет к репозиторию в настройках пакета).

Собирается только под `linux/amd64`. На PR образ только собирается, без пуша.

Локально:
```bash
make build                      # сборка в xjl00/backup-postgres-s3:latest
make push                       # сборка + push в Docker Hub
make push-all                   # сборка + push в Docker Hub и ghcr.io
make build IMAGE=ghcr.io/xjl0/backup-postgres-s3   # свой тег/реестр
```
Перед `make push*` нужен логин: `docker login` (Docker Hub) и/или `docker login ghcr.io -u <user>`
(в качестве пароля — токен).

> **Версии.** Клиент `pg_dump` должен быть **>= сервера**. `pg_dump` умеет дампить серверы
> **старее** себя (вплоть до 9.2), но **не новее**. Поэтому образ по умолчанию — с клиентом **PG18**,
> и один такой образ снимает **15/16/17/18**. Нужен пин под версию — `make build PG_MAJOR=16`
> (или `--build-arg PG_MAJOR=16`).

## Тесты (локальный стенд, без внешних сервисов)
`docker-compose.test.yml` поднимает **четыре сервера PostgreSQL — 15, 16, 17, 18** — у каждого свои
данные с фичами именно этой версии, и S3-совместимое хранилище. Образ бэкапа собирается из локального
`Dockerfile` (клиент PG18) и по очереди снимает все четыре сервера — как в реальности, когда один
образ обслуживает парк разных мажоров.

```bash
make test          # поднять стенд и прогнать: бэкап -> восстановление -> сверка данных -> retention
make test-logs     # лог прогона (уже завершившегося)
make test-ls       # что лежит в S3-стенде
make test-verify VER=pg15 DB=app   # отдельно перепроверить восстановление версии
make test-retention VER=pg18 KEEP_CHECK=2 KEEP_RUNS=5   # отдельно перепроверить retention
make test-faults    VER=pg18    # отдельно: падение pg_dump -> битый дамп не уезжает в S3
make test-real-s3              # проверка РЕАЛЬНОГО S3 из .env (см. ниже)
make test-down     # остановить и удалить данные стенда
```
Инфраструктура поднимается **detached**: прерывание прогона не роняет БД, а повторный `make test`
идёт за секунды (данные стенда сохраняются). Полный сброс — `make test-down`.

> `make test` собирает образ `runner` явно и запускает прогон через `run --no-deps`: так он не ждёт
> одноразовый `s3-init` (иначе `docker compose run` может «зависнуть» без вывода) и не роняет БД
> при Ctrl-C. Лог сохраняется в контейнере `pg-s3-backup-test` — посмотреть: `make test-logs`.

Что проверяется по каждой версии (всё в логе, код возврата `runner` = есть ли ошибки):

| Этап | Что видно в логе |
|---|---|
| Бэкап | конфигурация, версии, `zstd`-дамп, `verify` (zstd -t / pg_restore -l / полное чтение), `restore-test`, `upload OK ... размер сверен`, `retention` |
| Восстановление | `verify.sh`: скачивание дампа из S3, разворот в одноразовую БД на сервере **той же** версии |
| Данные | построчная сверка `источник vs восстановлено` по **каждой** таблице |
| Фичи версии | 15 — `MERGE`, `UNIQUE NULLS NOT DISTINCT`; 16 — SQL/JSON конструкторы, `random_normal()`; 17 — `JSON_TABLE`, GUC `transaction_timeout`; 18 — `uuidv7()`, виртуальные генерируемые колонки |
| Retention | заливаем `KEEP_RUNS` копий при `KEEP_CHECK` (`RUNS > KEEP`) и требуем, чтобы в S3 остались ровно `KEEP_CHECK` новейших, а старейшие были удалены (отдельный префикс, по умолчанию `2/5`) |
| Fault injection | подставляем «падающий» `pg_dump` (падает сразу и падает, отдав валидное оглавление + часть данных) и требуем, чтобы `backup.sh` вернул ненулевой код и **ничего не загрузил** в S3 |
| Уведомления | Проверка в S3 без egress | в логе подтверждение, что объект сверен по размеру, а для single-part — и по MD5/ETag; для multipart (PG17, ~13 МБ) подтверждается размер |

Стенд запускает S3-совместимое хранилище `adobe/s3mock` (данные только в контейнере). Любой другой
S3 подойдёт: чтобы взять MinIO, замените образ `s3` в `docker-compose.test.yml`.

### Проверка вашего реального S3 (`make test-real-s3`)
Мок не воспроизводит поведение конкретного провайдера, поэтому есть отдельная проверка против
**вашего** S3 из `.env` (endpoint/бакет/креды). Она:
- берёт креды через `--env-file .env` (в вывод не попадают);
- работает в **отдельном** префиксе (`REAL_PREFIX`, по умолчанию `test/reals3check`) и **отказывается**
  работать в `test`/`backup`, чтобы retention не задел существующие бэкапы;
- проверяет доступность бакета, `list`/`delete` (основа retention);
- главное — **диагностирует скачивание**: авторитетно проверяет, не ломается ли restore из-за
  поведение rclone при скачивании;
- прогоняет `backup.sh` против локального PostgreSQL в этот префикс и подтверждает выгрузку без
  скачивания (размер + MD5/ETag).

```bash
make test-real-s3                                  # префикс по умолчанию
make test-real-s3 REAL_PREFIX=test/mycheck REAL_KEEP=2
```

## Использование (в любом стеке)
```yaml
services:
  pg-backup:
    image: xjl00/backup-postgres-s3:latest   # зеркало: ghcr.io/xjl0/backup-postgres-s3
    restart: unless-stopped
    environment:
      PGHOST: "postgres-db"          # имя сервиса БД в сети
      PGUSER: "postgres"
      PGPASSWORD: "CHANGE_ME"
      S3_ENDPOINT: "https://s3.kz-1.srvstorage.kz"
      S3_REGION: "kz-1"
      S3_ACCESS_KEY_ID: "CHANGE_ME"
      S3_SECRET_ACCESS_KEY: "CHANGE_ME"
      S3_BUCKET: "my-backups"
      S3_PREFIX: "myapp"
      KEEP: "7"
    networks: [ backend ]            # та же сеть, что и БД
```
Никаких `volumes`/`configs`/`command` — всё внутри образа. Полный пример: `docker-compose.example.yml`.

## Переменные
| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PGHOST` / `PGPORT` / `PGUSER` / `PGPASSWORD` | — | подключение к БД |
| `ADMIN_DB` | `postgres` | служебная БД для перечисления баз / версии |
| `S3_ENDPOINT` | — | endpoint, напр. `https://s3.kz-1.srvstorage.kz` |
| `S3_REGION` | `us-east-1` | регион провайдера (напр. `kz-1`) |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | — | ключи доступа |
| `S3_BUCKET` | — | бакет (уже существует; скрипт его не создаёт) |
| `S3_PREFIX` | `backup` | подпапка в бакете |
| `KEEP` | `7` | копий каждой базы |
| `ZSTD_LEVEL` | `9` | уровень zstd (6=быстро … 19=плотнее) |
| `INTERVAL` | `86400` | секунд между прогонами |
| `EXCLUDE_DBS` | `postgres` | исключаемые базы |
| `DUMP_GLOBALS` | `1` | выгружать роли/привилегии |
| `VERIFY` | `1` | `zstd -t` + `pg_restore -l` перед загрузкой |
| `VERIFY_FULL` | `1` | + полное чтение архива локально (`pg_restore -f /dev/null`) — ловит обрыв данных. Трафика нет |
| `VERIFY_REMOTE` | `1` | проверка объекта в S3 **без скачивания**: размер + MD5 (для объектов < 200 МиБ) |
| `VERIFY_DOWNLOAD` | `0` | `1` = дополнительно **скачать** объект из S3 и проверить целиком (это исходящий трафик) |
| `RESTORE_TEST` | `0` | полный тест восстановления в скретч-БД |
| `RUN_ONCE` | `0` | `1` = один прогон и выход (код возврата = были ли ошибки); для тестов/CI |
| `WAIT_DB_TIMEOUT` | `0` | секунд ожидания БД при старте; `0` = ждать бесконечно |
| `EXTRA_PGDUMP_ARGS` | (пусто) | доп. флаги `pg_dump` (напр. `--enable-row-security`, `--no-large-objects`) |
| `ENV_FILE` | `/etc/pg-backup/env` | путь к файлу `KEY=VALUE` (см. ниже); переменные из окружения приоритетнее файла |

## Env-файл (альтернатива `environment:`)
Всё то же можно задавать не переменными окружения, а файлом `KEY=VALUE` — например, когда в swarm
stack-файл игнорирует `env_file:`. Скрипт читает такой файл (по умолчанию `/etc/pg-backup/env`,
путь можно переопределить `ENV_FILE`) и **не переопределяет** переменные, уже заданные в окружении —
приоритет как у `environment:` поверх `env_file:` в compose. Формат: строки `KEY=VALUE`, комментарии
`#`, пустые строки, необязательный префикс `export`, обрамляющие кавычки снимаются.

Готовый шаблон — `stack.env.example`:
```bash
cp stack.env.example stack.env   # stack.env в .gitignore
```

```yaml
# compose
    volumes:
      - ./stack.env:/etc/pg-backup/env:ro     # или задать ENV_FILE
```
```yaml
# swarm (stack-файл игнорирует env_file:, поэтому — томом)
    volumes:
      - /etc/pg-backup/env:/etc/pg-backup/env:ro
```
Оба способа можно смешивать: часть переменных — в `environment:`, часть — в файле.

## Проверка целостности (что и зачем)
Бэкап проверяется в несколько уровней — от дешёвого к самому надёжному. **По умолчанию данные из S3
не выкачиваются** (исходящий трафик платный): «сломан ли дамп» проверяется локально, а «доехал ли он
до S3» — по метаданным объекта.
0. **Код возврата `pg_dump`/`pg_dumpall`** проверяется отдельно от конвейера с `zstd`: в POSIX `sh`
   статус конвейера — это статус **последней** команды, поэтому падение `pg_dump` иначе остаётся
   незамеченным. Оборванный дамп (валидное оглавление + часть данных) проверками уровня `VERIFY`
   **не** ловится — только `VERIFY_FULL`.
1. **`zstd -t <file>`** — сжатый поток не повреждён (внутренние контрольные суммы zstd).
2. **`unzstd -c <file> | pg_restore -l`** — валидный архив pg_dump, читается оглавление (TOC).
3. **`VERIFY_FULL=1` (по умолчанию)** — `unzstd -c <file> | pg_restore -f /dev/null` читает **весь**
   архив (все данные), но ничего не исполняет; БД и права не нужны. Это и есть гарантия «дамп не
   сломан», и она **локальная** — трафика нет.
4. **После загрузки, без скачивания**: `rclone ls` по подпапке — сверяем размер объекта с локальным
   (ловит недолитую/отсутствующую загрузку). Трафика нет.
5. **`VERIFY_DOWNLOAD=1`** (по желанию, это **трафик**) — `rclone copy` объекта обратно и полная
   проверка архива. Разумно гонять изредка, а не каждый прогон.
6. **`RESTORE_TEST=1`** (по желанию) — реальное восстановление в **временную** БД-скретч и `dropdb`.
   Единственная 100%-я проверка «бэкап восстанавливается»; нужна роль с `CREATEDB` (или суперюзер).
   Восстанавливается **локальный** файл (до загрузки) — трафика нет.

Всё это логируется в stdout (`verify: ...`, `SHA256/MD5 сверен с S3`, `restore-test OK`, `upload OK`).
При провале любой проверки база помечается ошибкой, и дамп **не** загружается.

> **Про хранилище.** Выгрузка идёт через `rclone`, подключение задаётся переменными окружения
> (`S3_ENDPOINT`/`S3_REGION`/ключи) — файл `rclone.conf` не нужен.
> Если провайдер продаёт трафик на скачивание, держите `VERIFY_DOWNLOAD=0` (по умолчанию) — тогда
> данные из S3 не выкачиваются вообще: «не сломан ли дамп» проверяется локально, а доехал ли он —
> по размеру через `rclone ls`.

> Для абсолютной гарантии независимо от прогонов имеет смысл изредка делать ручной/отдельный
> тест восстановления — «бэкап, который не восстанавливали, — не бэкап».

## Восстановление
```bash
# скачать последнюю копию базы
rclone copy s3:backup-commercial-prod/<prefix>/<db>/ ./dump/ --include "<ts>.dump.zst"
unzstd -c ./dump/<ts>.dump.zst | pg_restore -l | less                    # посмотреть содержимое
unzstd -c ./dump/<ts>.dump.zst | pg_restore -h <host> -U <user> -d <target_db> -j4 --no-owner --no-privileges
rclone ls s3:backup-commercial-prod/<prefix>/_globals/                 # список globals-дампов
unzstd -c <ts>.sql.zst | psql -h <host> -U <user> -d postgres            # роли
```
`<db>.dump.zst` — custom-формат pg_dump, целиком сжатый zstd; `pg_restore` напрямую `.zst` не читает,
поэтому распаковываем через `unzstd -c | pg_restore`.

## Версии PostgreSQL и права (важно)
- **Клиент `pg_dump` >= сервера.** Клиент может дампить серверы старее себя (до 9.2), но не новее.
  Один образ PG18 закрывает 15/16/17/18. Скрипт сам читает `server_version_num`, логирует
  сервер/клиент и при `сервер > клиент` пропускает прогон с понятной ошибкой (нужен образ с нужным `PG_MAJOR`).
- **Кросс-версии** (мажор клиента ≠ сервера): скрипт сам добавляет `--quote-all-identifiers` —
  рекомендовано документацией, снимает часть минорных различий.
- **Не-суперюзер.** Для данных нужны `CONNECT` на каждую БД + чтение; проще всего выдать
  `GRANT pg_read_all_data TO <роль>` (есть с PG14). Скрипт определяет права и предупреждает,
  если у роли нет `SUPERUSER`/`pg_read_all_data`. `pg_dumpall` идёт с `--no-role-passwords`
  (пароли ролей не читаются — суперюзер не нужен).
- **RLS.** Если в БД есть row-level security, `pg_dump` без `BYPASSRLS` упадёт. Скрипт предупредит
  заранее; варианты: выдать роли `BYPASSRLS` или `EXTRA_PGDUMP_ARGS="--enable-row-security"`
  (тогда выгрузятся только доступные строки — дамп неполный).
- **Large objects** у не-суперюзера могут не выгрузиться (зависит от версии/прав) — при использовании
  `lo` проверьте отдельно.
- **Кросс-версия при restore.** Клиент новее сервера кладёт в дамп `SET <guc> = 0` для параметров,
  которых в старом сервере нет (напр. `transaction_timeout` из PG17+ при restore в PG15/16).
  `pg_restore` об этом сообщает и продолжает; скрипт в `RESTORE_TEST` такие ошибки провалом не считает.
  Для «чистого» восстановления в старый мажор удобнее образ с клиентом того же мажора (`PG_MAJOR`).
- **`RESTORE_TEST` требует `CREATEDB`** у роли (или SUPERUSER); иначе тест корректно пропускается
  с предупреждением.

## Нюансы (грабли, уже учтены в коде)
- **Сжатие внешним zstd** по всему архиву, а не `-Z zstd` внутри: встроенное жмёт по сегментам и на
  мелких/средних базах проигрывает в разы.
- **path-style** обязателен для части S3-совместимых хранилищ — выставляется в скрипте.
- В swarm `restart`/`container_name`/`depends_on` игнорируются — используется `deploy.*` и `pg_isready`.
- Логи: swarm — `docker service logs -f <stack>_pg-backup`, compose — `docker compose logs -f pg-backup`.
